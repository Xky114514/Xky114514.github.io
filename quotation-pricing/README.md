# AI 报价定价助手 · 前端交互原型

一个以对话为主的报价决策工作台，用于验证“查看依据 → 调整报价 → 人工确认 → 管理策略生效 → 人工落实与核验”的业务流程。

**当前是离线前端原型。** 客户、价格、来源记录和协议均为演示数据；没有接入真实大模型、企业微信或 ERP，也不会发消息、抓取实时行情或自动写回业务系统。

## 业务背景

### 面向什么业务

本产品面向配送公司中负责为不同商户制定、确认报价的负责人。一次报价通常涉及一个客户、多个商品规格及一个适用周期；负责人需要综合采购成本、历史成交、市场与供应情况、客户经营情况、协议及业务条件，确定每个商品最终报多少。

同一商品对不同客户的报价，需要结合采购量、采购频率、配送要求、规格、账期及有效约定分别判断。成本变化可能支持重新评估价格，长期合作关系可能支持控制调幅，有效固定价协议则可能直接限制本次报价。这些因素需要说明依据和取舍，不能无依据地换算成统一加减价。

### 当前要解决的问题

| 业务问题 | 产品希望提供的帮助 |
| --- | --- |
| 系统数据、采购资料、市场信息和沟通记录分散 | 按本次订单、客户和商品规格汇集，让负责人减少寻找与整理资料 |
| 来源的时间、单位、税价或商品规格不同 | 先核对适用对象和比较口径，明确缺项及不适用资料 |
| 多个因素影响方向不同，单一价格难以说明原因 | 展示因素影响、参考区间、上下沿前提和经营取舍 |
| 新消息或经营考虑可能改变判断 | 通过多轮对话补充与纠正信息，只更新相关建议，保留人工决定 |
| 不同客户使用不同报价，策略又有生效时间 | 集中查看客户策略与历史，检查同客户时间冲突，避免版本和时段混用 |
| 确认价格与实际录单是两个环节 | 保留确认版本、人工落实及核验记录，发现实际执行差异 |

### 谁使用、谁负责

- **配送负责人**是主要使用者：查看依据、讨论方案、决定具体价格，确认报价版本和策略安排；最终定价权始终属于负责人。
- **资料提供与整理人员**提供或汇集采购、客户、市场和沟通信息，保留来源、日期、适用条件及核实状态。
- **原系统执行人员**将已确认报价人工落实到业务系统，并提供实际录单记录供核验。原型中的角色说明不代表已实现账号与权限管理。

在界面中，“客户”对应被报价的商户；“本次订单／报价单”组织该客户本次待定价的商品；“报价策略”保存一套已确认价格及其生效安排。对话中的一次调整先进入草稿，不能直接当作已经生效的策略。

### 产品目标与首轮验证范围

方案的核心目标是：汇集与本次报价有关的信息，说明哪些因素影响价格、如何影响以及有哪些取舍，辅助负责人更清楚、更省时地作出决定。

产品始终分别保留 **客观参考资料、AI 定价建议、负责人最终决定**。负责人采纳建议或利用整理后的依据自主定价，都是有效路径；评价重点是判断是否更清楚、流程是否更省时、报价能否正确落实，不能只看 AI 价格采纳率。

首轮业务试跑拟选择 **1 家配送公司、少量现有商户的一次完整报价任务**：系统资料采用现有导出，企业微信提供沟通补充，外部资料由服务人员从指定来源人工汇集。首轮重点验证多源信息关联、建议可解释性、多轮讨论及最终落实的完整流程。

业务方案中的 AI 能力是后续真实接入的目标；当前 HTML 用演示数据和限定规则验证交互。企业微信是信息来源与交流入口之一，企微消息本身不直接等同于有效约定或调价指令。

## 快速启动

无需安装依赖或构建，下载本目录后，用现代浏览器打开 `index.html` 即可使用。

如希望通过本地 HTTP 访问，可在本目录运行：

```sh
python -m http.server 8080 --bind 127.0.0.1
```

然后打开 <http://127.0.0.1:8080>。GitHub 文件页展示的是源代码，需下载后在浏览器打开；本次代码上传不等于部署网站。

推荐使用 Edge 或 Chrome。直接打开文件时，如果浏览器限制本地存储，可改用上面的 HTTP 方式。

## 页面设计

| 页面 | 使用方式 |
| --- | --- |
| 报价对话 | 选择客户，输入自然语言或使用结构化规则；查看商品变更预览，再应用到草稿 |
| 客户与依据 | 客户单选下拉展示名称、商品数、依据标签；五类卡片汇总整单，点击后进入商品明细、来源与调整入口 |
| 报价策略 | 统一查看各客户当前、待生效、待设置和历史策略，设置有效期、停用、处理重叠与追溯记录 |

整张报价单默认在侧面板中收起。当前执行价、AI 参考和负责人最终价分开显示。客观依据涵盖采购成本、历史价格、市场供应、商户情况、协议与业务条件，来源入口提供可阅读的示例记录。

## 五分钟试用

1. 选择 **云栖酒店**，进入“客户与依据”，点开卡片查看商品及来源。
2. 回到“报价对话”，输入 `全部商品按当前价上调3%`。
3. 检查商品范围、计算基准及拟定价格，点击“应用到草稿”。此时还未正式确认，可继续修改或撤销。
4. 点击“存为策略”，填写名称；也可输入 `保存为“国庆保供策略”`。
5. 点击“确认报价”，审阅具体价格、条件及未解决项后确认。
6. 进入“报价策略”，找到刚确认的策略，设置开始和结束时间，选择是否启用。
7. 如果时间与该客户已有策略重叠，先查看替换影响；取消不会修改原安排，确认后才应用。
8. 切换另一客户制定不同策略，在策略页比较；需要落实时，记录原系统的人工录单信息并核验。

其他可试输入：

```text
把蔬菜按当前价上调3%，协议价不动
大白菜改成5.40元/斤
大白菜和土豆按当前价上调3%
查看报价策略
```

规则解析是有限范围实现。范围、基准、单位或计算方式不清时，会要求澄清或转入“按条件调整”。批量排除的协议商品可能尚未填写最终价，整版确认前需补齐。

## 策略与时间规则

- 草稿不能直接生效；确认整版报价后，保存独立的价格、依据和规则记录。
- 不同客户可同时生效；**同一客户、同一时段最多一套生效策略**。
- 时间按北京时间解释，采用 `[开始时间, 结束时间)`；前一策略结束与后一策略开始相同允许衔接。
- 重叠安排需明确确认替换。旧策略可能提前结束或取消未来启用；不会自动恢复原策略剩余时段。
- 生效后不能改写已发生的开始时间；尚未发生的结束时间可调整并留档。
- 未开始就取消的策略保留原计划及取消时间；历史策略通过复制重新安排。
- “从现在开始”以实际确认时刻衔接，避免用户停留在确认弹窗时回填过去时间。
- 来源报价周期固定为 **2026 年 10 月 1—7 日**。超期复用须重新核对整版价格及业务条件，单独保存新时段确认，原报价版本不变。
- 鲜鸡蛋示例协议适用 **2026 年 10 月 1—31 日**。正式确认策略超出该协议期间时，界面会阻止启用并提示核实新约定；当前原型没有真实协议续签功能。
- 演示中的现行和历史示例策略按首次打开时的时间初始化，并标为“演示”。未来再次试用时，请选择未过去的时间；云栖酒店场景适合体验跨期复核。
- 策略安排与原系统执行独立：启用策略不会自动录单，仍需人工落实及核验。

## AI 在这里的作用

产品设计上，AI 用于理解报价意图、整理多源依据、解释参考区间和取舍、提出必要的澄清问题；使用者决定具体价格和是否生效。价格计算、协议限制和时间重叠必须通过确定性程序规则检查。

**当前实现**使用浏览器内的限定规则解析和预设参考数据，没有真实模型调用、API Key、模型推理或后台服务。参考解释不是实时 AI 生成，不能当作真实经营报价依据。

## 技术与数据

- 单文件 HTML，内嵌 CSS、JavaScript 和 SVG 图标，无运行时外部依赖。
- 草稿、对话、确认版本、策略与记录使用浏览器 `localStorage` 保存，键为 `pricing-assistant-conversation-v2`。
- 支持读取此前 `pricing-assistant-light-v1` 的本地演示记录。清除浏览器数据会丢失记录。
- 不同浏览器、设备、文件路径或 HTTP 端口的存储可能不同，不提供跨设备同步。
- 如需重置，打开页面底部“演示回复”或左下角用户信息，进入“关于本演示 → 重置演示”。
- 生效状态根据当前时间在页面内计算；没有服务端定时任务、多人并发保护、权限审批或真实审计存储。

## 已完成的验证

通过 Edge 的实际界面操作验证了客户切换、整单依据下钻、来源阅读、单商品及批量调整、撤销、策略命名与确认、重叠替换、跨客户隔离、有效期调整、历史保护、本地保存、人工落实及录单差异核验。检查了桌面、390 和 320 像素宽度的布局。

试用中修复了未来取消导致的时间倒置、跨期复用缺少复核、协议期限遗漏、到期停用改写历史和延迟确认时间衔接等问题。详细过程见 [试用记录](docs/user-trial.md)，设计说明见 [设计文档](docs/design.md)。

上述验证针对本地原型，不代表真实 AI、后端、多用户或 ERP 集成已完成。后续接入时需补充服务端校验、授权、持久化和真实资料来源管理。
